# CONSTRUCTING API REQUESTS

Successfully interacting with the Weir AI API hinges on correctly constructing your HTTP requests. This section provides detailed guidance on how to formulate these requests, covering the base URL structure, essential HTTP headers, data formatting for request bodies, and the use of query parameters. For the engineering team, understanding these components is fundamental to building reliable integrations and for debugging any communication issues. AI agents will also rely on this structured information for programmatic request generation.

## UNDERSTANDING BASE URLS AND ENDPOINTS

All API requests to Weir AI are directed to a specific base URL, with individual functionalities accessed via specific paths known as endpoints.

### Base URL Structure

The base URL for the Weir AI API will be consistent across all endpoints for a given environment (e.g., sandbox, production) and API version.

<CardGroup cols={2}>
    <Card title="Production Base URL" icon="Cloud">
        <CodeBlock>{`https://api.weir.ai/v1`}</CodeBlock>
    </Card>
    <Card title="Sandbox Base URL" icon="Flask">
        <CodeBlock>{`https://sandbox.api.weir.ai/v1`}</CodeBlock>
    </Card>
</CardGroup>

<Warning title="HTTPS is Mandatory">
    As emphasized in Section 3.2.2, all communication **must** occur over HTTPS to ensure data encryption and security.
</Warning>

**API Versioning in URL:** The API version (e.g., `v1`) is typically included directly in the base URL path. This allows us to introduce new API versions without breaking existing integrations. Details on API versioning are covered in Section 3.7. The engineering team should ensure their client configurations can easily adapt to new versions if needed.

### Endpoints

Endpoints are specific paths appended to the base URL that correspond to particular resources or operations. Each endpoint represents a distinct function you can perform.

**Example:**
If the base URL is `https://api.weir.ai/v1` and you want to access the "jobs" resource:
- The endpoint path might be `/jobs`.
- The full URL for creating a new job via a POST request would then be:
    <CodeBlock lang="bash">{`POST https://api.weir.ai/v1/jobs`}</CodeBlock>
- To retrieve a specific job with ID `job_123xyz` via a GET request:
    <CodeBlock lang="bash">{`GET https://api.weir.ai/v1/jobs/job_123xyz`}</CodeBlock>

<Tip>
    The complete list of available endpoints, their specific paths, supported HTTP methods, and required parameters are detailed in **Section 4: API Endpoint Reference**. The engineering team should treat Section 4 as their primary reference for endpoint-specific details.
</Tip>

## HTTP HEADERS (COMMON AND WEIR AI SPECIFIC)

HTTP headers are a crucial part of an API request, providing metadata about the request itself, such as authentication credentials, the desired response format, and the type of content being sent.

### Standard Essential Headers

<AccordionGroup>
    <Accordion title="Authorization" icon="Key" defaultOpen={true}>
        - **Purpose:** Carries the credentials to authenticate the client. As detailed in Section 3.2.2, Weir AI primarily uses Bearer Token authentication.
        - **Example:** <CodeBlock>{`Authorization: Bearer <YOUR_API_KEY>`}</CodeBlock>
        - **Requirement:** Mandatory for all protected endpoints.
    </Accordion>
    <Accordion title="Content-Type" icon="FileCode" defaultOpen={true}>
        - **Purpose:** Specifies the media type of the request body (e.g., for POST, PUT, PATCH requests). For Weir AI, this will almost always be JSON.
        - **Example:** <CodeBlock>{`Content-Type: application/json; charset=utf-8`}</CodeBlock>
        - **Requirement:** Mandatory if the request includes a body. It's good practice to include `charset=utf-8` to ensure proper handling of various character sets.
    </Accordion>
    <Accordion title="Accept" icon="FileArrowDown" defaultOpen={true}>
        - **Purpose:** Informs the server about the media type(s) the client can understand in the response. While clients can send a list of acceptable types, Weir AI will primarily respond with JSON.
        - **Example:** <CodeBlock>{`Accept: application/json`}</CodeBlock>
        - **Requirement:** While not always strictly mandatory for the request to be processed (as the server might default to `application/json`), it's highly recommended to include it to ensure your client explicitly states its expected response format. This helps prevent misinterpretations if the API were to support multiple response formats in the future.
    </Accordion>
</AccordionGroup>

### Common Optional/Conditional Headers

<AccordionGroup>
    <Accordion title="User-Agent" icon="IdentificationBadge">
        - **Purpose:** Provides information about the client making the request (e.g., application name, version, library used). This can be very helpful for Weir AI support teams in diagnosing issues specific to certain clients.
        - **Example:** <CodeBlock>{`User-Agent: MyAwesomeApp/1.2.0 WeirAI-Python-SDK/1.0.0`}</CodeBlock>
        - **Recommendation for the engineering team:** Encourage setting a descriptive `User-Agent` string. This can significantly aid in troubleshooting if issues arise. For AI agents, this could include the agent's name and version.
    </Accordion>
    <Accordion title="Idempotency-Key" icon="Repeat">
        - **Purpose:** As discussed in Section 3.1.4, this header can be used to ensure that POST operations are executed only once, even if the request is retried due to network issues.
        - **Example:** <CodeBlock>{`Idempotency-Key: a_unique_string_for_this_operation_attempt`}</CodeBlock>
        - **Requirement:** Only applicable and effective for specific POST endpoints that explicitly support it (see Section 4 for details). The key should be a unique string generated by the client for each distinct operation attempt.
    </Accordion>
    <Accordion title="X-Request-ID or Correlation-ID" icon="Link">
        - **Purpose:** A unique identifier generated by the client for a specific request. If the client logs this ID and Weir AI includes it in its logs and potentially in the response headers, it greatly facilitates tracing a request through various systems for debugging.
        - **Example:** <CodeBlock>{`X-Request-ID: abc123xyz789-uuid-format`}</CodeBlock>
        - **Recommendation for the engineering team:** If your applications generate correlation IDs, including them in requests to Weir AI can be beneficial for end-to-end traceability.

</AccordionGroup>

## REQUEST BODY: DATA FORMATTING (JSON)

For API requests that create or update resources (POST, PUT, PATCH), data is sent to the server in the request body.

### JSON (JavaScript Object Notation) is the Standard

The Weir AI API exclusively uses JSON (`application/json`) as the data format for request bodies. JSON is lightweight, human-readable, and widely supported by programming languages and HTTP client libraries.

The engineering team should ensure that any data structures (objects, arrays, etc.) are correctly serialized into a valid JSON string before being sent in the request body. Most HTTP client libraries handle JSON serialization automatically if provided with a native data structure (like a Python dictionary or a JavaScript object).

<AccordionGroup>
    <Accordion title="Structure and Content" icon="BracketsCurly" defaultOpen={true}>
        The specific structure (fields, data types, nesting) of the JSON body required for each endpoint is defined in **Section 4: API Endpoint Reference**. This includes details on mandatory fields, optional fields, data type constraints (e.g., string, integer, boolean, array, object), and any specific format requirements (e.g., ISO 8601 for dates).
        **Example (conceptual for creating a job):**
        <CodeBlock lang="json">
            {`{
                "job_name": "Monthly Sales Analysis",
                "dataset_id": "ds_abc123",
                "model_parameters": {
                    "algorithm": "predictive_forecast_v2",
                    "lookback_window": 30
                },
                "notification_email": "engineer@example.com"
            }`}
        </CodeBlock>
    </Accordion>
    <Accordion title="Character Encoding" icon="TextAa">
        Always use UTF-8 encoding for JSON request bodies. This is typically specified in the `Content-Type` header: <CodeBlock>{`Content-Type: application/json; charset=utf-8`}</CodeBlock>.
    </Accordion>
    <Accordion title="Empty Body" icon="FileDashed">
        If an endpoint using POST, PUT, or PATCH does not require any data in the body (which is rare but possible for certain command-like operations), an empty JSON object `{}` might be expected, or the `Content-Type` header might still be required even with an empty body. Consult the specific endpoint documentation in Section 4. GET and DELETE requests should NOT have a request body.
    </Accordion>
    <Accordion title="Data Validation" icon="CheckSquareOffset">
        The Weir AI API server will validate the structure and content of the JSON request body. If the JSON is malformed, missing mandatory fields, or contains fields with incorrect data types, the API will typically respond with an HTTP `400 Bad Request` status code. The response body of the error should provide specific details about the validation failures to help the engineering team correct the request.
    </Accordion>
</AccordionGroup>

## QUERY PARAMETERS

Query parameters are used to pass additional information or modify the behavior of an API request, typically for GET requests to filter, sort, or paginate collections of resources. They are appended to the URL after a question mark (`?`) and are specified as `key=value` pairs, separated by ampersands (`&`).

### Purpose

<CardGroup cols={2}>
    <Card title="Filtering" icon="Funnel">
        Narrow down results from a collection.
        E.g., <CodeBlock>{`GET /api/v1/jobs?status=completed`}</CodeBlock>
    </Card>
    <Card title="Pagination" icon="ListNumbers">
        Control items returned and request specific pages. Details in Section 3.4.4.
        E.g., <CodeBlock>{`GET /api/v1/logs?limit=100&offset=200`}</CodeBlock>
    </Card>
    <Card title="Sorting" icon="SortAscending">
        Specify result order.
        E.g., <CodeBlock>{`GET /api/v1/events?sort_by=timestamp&order=desc`}</CodeBlock>
    </Card>
    <Card title="Selecting Fields (if supported)" icon="ListChecks">
        Request specific fields to reduce response size.
        E.g., <CodeBlock>{`GET /api/v1/users/{userId}?fields=id,name,email`}</CodeBlock>

### Format
<CodeBlock>{`https://api.weir.ai/v1/resource?param1=value1&param2=value2`}</CodeBlock>

<AccordionGroup>
    <Accordion title="URL Encoding" icon="LinkSimpleHorizontalBreak">
        Values for query parameters **MUST** be URL-encoded (percent-encoded), especially if they contain special characters, spaces, or reserved characters (e.g., `&`, `?`, `=`, `/`, `%`). Most HTTP client libraries handle this automatically.
        **Example:** To filter by `job_name=My Job & Co`, it should be encoded as:
        <CodeBlock>{`job_name=My%20Job%20%26%20Co`}</CodeBlock>
    </Accordion>
    <Accordion title="Available Parameters" icon="ListDashes">
        The specific query parameters supported by each endpoint (names, data types, behavior) are detailed in **Section 4: API Endpoint Reference**. Using unsupported query parameters will typically be ignored or may result in an error if strict parameter checking is enforced.
    </Accordion>
    <Accordion title="Case Sensitivity" icon="TextAUnderline">
        Query parameter keys are often case-sensitive. Match the case exactly as specified in the API documentation. Values may or may not be case-sensitive depending on the specific parameter.
    </Accordion>
</AccordionGroup>
